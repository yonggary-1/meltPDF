# meltPDF v0.10.2

**작은 빌드입니다: 메모리에 두는 RAR/CBR은 디스크 임시 폴더 없이 바로 받습니다.**

1. **RAR/CBR 메모리 직접 받기** (`rar_tool.py`의 `open_stream`, `archive_rar.py`의 `_stream_images`): 이전에는 메모리 방식이어도 RAR는 임시 폴더에 전부 풀었다가 읽었습니다(RAR를 풀 수 있는 파이썬 라이브러리가 없어서). 이제 메모리에 두는 경우 같이 들어 있는 UnRAR의 `p` 명령(파일 내용을 표준 출력으로 내보냄)으로 받아, 이미지만 메모리에 담고 이미지가 아닌 파일은 버립니다. 파일 경계는 목차의 크기로 자르고, 이미지는 CRC32까지 맞는지 확인합니다. 종료 코드가 0이 아니거나 크기/체크섬이 하나라도 어긋나거나 링크·같은 이름의 중복이 있으면, 받은 것을 버리고 예전 방식(디스크 임시 폴더)으로 되돌아갑니다. 그래서 손상된 rar의 처리(읽힌 데까지 불러오고 빨간 테두리)는 이전과 같습니다. 디스크 방식을 고른 경우와 7-Zip 등 다른 도구를 쓰는 경우도 이전과 같습니다.
2. 이유: "RAR이 항상 램디스크를 쓰게 할 수 없나"라는 요청에서 출발했습니다. 진짜 RAM 디스크는 드라이버/관리자 권한이 필요해 프로그램이 만들 수 없어, 같은 목적(SSD/HDD에 쓰지 않기)을 UnRAR의 표준 출력으로 이뤘습니다.

**확인한 것:** 가상 화면이 필요 없는 단위 시험(Linux, rar 7.00으로 만든 RAR5)으로 확인했습니다.
- RAR5 일반/연속(solid)/무압축 3종, 하위 폴더, 한글 파일 이름, 이미지 아닌 파일과 빈 파일 포함: 메모리 방식 결과가 원본과 바이트까지 같고(5개), 임시 폴더를 만들지 않으며, 진행 표시가 끝까지 감. 디스크 방식 결과도 같음.
- 되돌아가기: 엉뚱한 크기를 내는 도구, 종료 코드 3을 내는 도구는 디스크 방식으로 되돌아가 결과가 같음. 모든 도구가 실패하면 이전과 같은 오류 안내. 끝이 잘린 rar와 저장된 이미지 한 바이트를 바꾼 rar는 이전과 같이 디스크 방식에서 손상으로 표시됨.
- 5MB 이미지 40장(200MB, solid): 메모리 직접 받기 1.59초, 디스크 경유 2.15초(이 환경의 숫자).
- 같이 들어 있는 `tools/UnRAR.exe`를 Wine으로 실행해 같은 방법으로 받아 보니 CRC32까지 맞게 받아짐(3종 모두).

**확인하지 못한 것:**
- **실제 Windows:** Wine으로만 확인했습니다. Windows에서 표준 출력이 바이트를 바꾸면 CRC가 어긋나 자동으로 디스크 방식으로 되돌아가므로 잘못된 이미지가 들어가지는 않지만, 되돌아가면 이점(디스크에 안 씀)이 없어집니다. 실제 Windows에서 이 방식으로 받았는지는 확인하지 못했습니다.
- RAR3/4 형식: 이 환경의 rar 7.00이 만들지 못해 시험하지 못했습니다(UnRAR는 읽을 수 있고 실패하면 디스크 방식으로 되돌아갑니다).
- 여러 권으로 나뉜 rar, 암호 rar(원래 거절), 파일을 열 때 메모리가 부족한 경우는 시험하지 못했습니다.
- 이번에도 이미지 보기·키 이동 시험은 다시 돌리지 못했습니다(해당 코드는 바꾸지 않았습니다).

### 받는 방법
이 릴리스의 소스는 위 태그(`v0.10.2`)의 소스 코드입니다. 압축을 풀고 폴더 구조를 그대로 둔 채 `build.bat`을 더블클릭하면 `dist\meltPDF.exe`가 만들어집니다(Python 3.9 이상 필요, 인터넷 필요). 자세한 사용법은 README.md, 전체 변경 이력은 CHANGELOG.md, 외부 소프트웨어 출처는 THIRD_PARTY_NOTICES.md를 보세요.
