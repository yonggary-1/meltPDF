# meltPDF v0.10.1

**작은 정리 빌드입니다: 하단 상태바에 메모리 미터, PDF 내보내기 메모리 절반으로, 끝이 잘린 zip 복구, 공식 LICENSE 파일, 좁은 창에서 버튼이 사라지던 문제 수정.**

1. **하단 상태바 메모리 미터** (새 파일 `ram_meter.py`, `memory_info.py`에 함수 추가): 오른쪽 아래에 "메모리 245MB | PC 63%"와 막대가 보입니다. 앞은 이 프로그램이 지금 실제로 쓰는 메모리, 뒤와 막대는 컴퓨터 전체 메모리 사용률입니다. 1.5초마다 갱신하며 값을 알 수 없는 환경이면 보이지 않습니다.
2. **좁은 창에서 [이미지 내보내기] 버튼이 사라지던 문제 수정** (`status_bar.py`, `app_window.py`): v0.10.0에서 창을 최소 폭(760px)으로 줄이면 상태 문구가 자리를 다 차지해 [이미지 내보내기] 버튼이 폭 1픽셀로 눌려 보이지 않았습니다(v0.10.0 코드에서 직접 재현). 상태 문구를 윗줄로 올리고 버튼과 메모리 미터를 아랫줄에 두었습니다. 같은 폭에서 위쪽 안내문이 잘리던 것도 줄바꿈되게 했습니다.
3. **PDF 내보내기 메모리 절반으로** (`pdf_core.py`): 이전에는 페이지마다 PDF를 만들어 모두 메모리에 쥐고 있어서 이미지 총량의 약 2배를 썼습니다. 이제 이미지를 묶음(최대 96MB 또는 200장)으로 임시 파일 PDF로 만든 뒤 옮기며, 사용량이 약 1배(= 결과 PDF 크기)입니다. 결과 PDF는 이전과 같습니다. 임시 파일은 끝나면(실패해도) 지웁니다.
4. **끝이 잘린 zip/cbz 복구** (새 파일 `zip_recover.py`, `archive_zip.py`): zip은 목차가 파일 끝에 있어서 다운로드가 끊기면 아예 열리지 않았습니다. 이제 목차를 못 읽으면 파일 앞에서부터 각 파일의 머리를 따라가며 읽을 수 있는 이미지를 꺼냅니다. 마지막이 중간에서 끊긴 이미지는 읽히는 부분만 불러와 빨간 테두리로 표시하고, "압축 파일의 끝부분(목차)이 손상되어 앞에서부터 읽어 복구했습니다" 안내가 정보 창에 함께 나옵니다. 목차가 정상인 zip은 이전과 같은 경로입니다. 저장/deflate 방식과 데이터 설명자(크기를 나중에 적는 방식)를 처리합니다(zip64 크기 읽기도 코드에 있으나 시험하지 못했습니다). 다른 압축 방식(bzip2/lzma 등)과 암호 zip은 지원하지 않습니다.
5. **`LICENSE` 파일 추가:** GNU AGPL v3 공식 원문입니다. GitHub의 `github/choosealicense.com`과 `spdx/license-list-data`에서 받아 공백을 무시하고 대조했고, 차이는 FSF 주소의 `http`/`https` 세 군데뿐이어서 최신 표기를 썼습니다. README와 THIRD_PARTY_NOTICES에도 반영했습니다.

**확인한 것:** 가상 화면(Xvfb)에서 시험했습니다.
- 메모리 미터: 300MB를 할당하면 측정값이 300MB 늘고, 해제하면 다시 줄며, 사용자가 건드리지 않아도 타이머가 갱신함. 760px와 1000px 폭에서 하단 버튼과 미터가 모두 보임(스크린샷, v0.10.0 코드에서는 760px에서 이미지 내보내기가 폭 1로 사라지는 것도 확인).
- PDF 메모리: 이미지 80장(합계 238MB)을 내보낼 때 늘어난 메모리 측정(Linux, 순수 메모리 기준). 이전 약 471MB → 이후 약 232MB, 이미지 240장(715MB) 기준 약 1433MB → 약 717MB, 디스크에서 읽을 때도 비슷함.
- PDF 결과 동일성: 이전과 새 코드로 같은 입력(JPEG/투명 PNG/DPI 있는 이미지/EXIF 회전/GIF/BMP, 표지 지정, 기존 PDF 페이지가 섞인 목록, 묶음을 2장씩 쪼갠 경우 포함)을 내보내 페이지 크기, 이미지 스트림 바이트, 페이지 내용이 모두 같음. 임시 폴더가 남지 않음(성공/실패 모두).
- 잘린 zip: deflate/stored 각각 일반 형식과 데이터 설명자 형식으로 만든 zip의 목차를 자르면 이미지 5개가 원본과 바이트까지 같게 복구됨, 데이터 중간에서 자르면 그 항목만 손상으로 표시되고 읽힌 부분이 원본의 앞부분과 일치함, 항목 머리 중간에서 자르면 그 앞까지 복구됨, 데이터가 바뀐 항목은 손상으로 표시됨, 일본어(cp932) 이름 복원됨, 이미지 아닌 파일 무시, 쓰레기/빈 파일은 이전 오류 안내 그대로, 정상 zip은 복구 안내가 나오지 않음, 60장 복구 0.03초. 실제 끌어다 놓기로 안내창 한 개(손상 1개 + 복구 안내)와 빨간 테두리 확인.
- 회귀: 이름 복원 13종, 이미지 내보내기 단위/화면 시험, 설정·원본 폴더·이름 변경 회귀, 중앙 목차가 정상인 zip 안의 손상 항목 표시.

**확인하지 못한 것:**
- **Windows:** 메모리 미터의 Windows용 호출(`GetProcessMemoryInfo`, `GlobalMemoryStatusEx`)은 이 환경에서 실행할 수 없어 코드 검토만 했습니다. Windows에서 값이 안 나오면 미터가 보이지 않을 뿐 다른 기능에는 영향이 없습니다. PDF 메모리 측정도 Linux 기준이며 Windows의 숫자는 다를 수 있습니다(줄어드는 방향은 같다고 봅니다).
- PDF 메모리는 1배(결과 PDF 크기) 아래로 줄이지 못했습니다. pikepdf가 페이지를 옮길 때 이미지 데이터를 메모리로 복사하는 것(파일을 mmap으로 열어도 같음)과 img2pdf가 만드는 동안 이미지를 메모리에 두는 것 때문입니다.
- 이번에 쓴 시험 자료가 환경 초기화로 한 번 사라진 뒤라, rar/손상 rar 시험과 이미지 보기·키 이동 시험은 이번 변경 후에 다시 돌리지 못했습니다(해당 코드는 이번에 바꾸지 않았습니다).
- 끝이 잘린 zip에서 zip64 큰 파일, bzip2/lzma 압축, 파일 앞에 다른 데이터가 붙은 자동 압축 해제 파일은 시험하지 못했습니다.

### 받는 방법
이 릴리스의 소스는 위 태그(`v0.10.1`)의 소스 코드입니다. 압축을 풀고 폴더 구조를 그대로 둔 채 `build.bat`을 더블클릭하면 `dist\meltPDF.exe`가 만들어집니다(Python 3.9 이상 필요, 인터넷 필요). 자세한 사용법은 README.md, 전체 변경 이력은 CHANGELOG.md, 외부 소프트웨어 출처는 THIRD_PARTY_NOTICES.md를 보세요.
